# 07: KMRP's 768x768 GUI textures at a power-of-two size

Under Proton on the handheld the game died every time the workbench upgrade screen opened: an abort inside the graphics driver with glibc's "corrupted double-linked list", raised while the game uploaded KMRP's `lbl_wupgradeb2.tga` through `gluBuild2DMipmaps`. That texture is 768x768, so wine's GLU rescales it to 1024x1024 before the driver sees it. With 1024x1024 copies of the two upgrade backgrounds in Override, where they take precedence over KMRP's bank, the screen opened and worked; but so did it afterwards with the originals back, and the difference between the runs that died and the runs that did not is more likely the session's history (both crashes came at the end of play from the Endar Spire into the apartment; every clean run loaded a save inside the apartment). So this repair is a candidate, not a proven fix, until the same route is played both ways. `lbl_custpnl.tga` (character creation's custom panel, the only other 768x768 file in the bank) gets the same treatment; the Feats-screen crashes earlier in this build happened on that screen.

What writes outside its allocation on that path is not proven. Until that is known, this keeps the three files out of the rescaling path. What is known:

- **Wine's GLU is not it.** Wine's `dlls/glu32/mipmap.c` (Proton 11's branch, `ValveSoftware/wine` `proton_11.0`), built natively under AddressSanitizer with the GL calls stubbed and a stub `glTexImage2D` that reads every byte a driver would, takes 768x768 to 1024x1024 (and 2868x1436 to 2048x1024) in RGB, BGR, RGBA and BGRA at unpack alignments 1 and 4 without one out-of-bounds read or write.
- **The abort is the driver's, during a texture upload.** The first crash's stack, read from raw stack memory and symbolized against the handheld's own `libgallium-25.2.4.so` through its embedded `.gnu_debugdata` symbols (its build is Bazzite's, which Fedora's debuginfod does not have), is radeonsi creating a texture for an upload: `u_default_texture_subdata` → `si_texture_transfer_map` → `si_texture_create_object` → `si_alloc_resource` → `amdgpu_bo_create` → `pb_slab_alloc` → `amdgpu_bo_slab_alloc` → glibc's abort. No GLU frame is among them, so "through `gluBuild2DMipmaps`" is not shown either; the executable references its `gluBuild2DMipmaps` import from nowhere in `.text`.
- **The heap that is corrupted is glibc's.** The game, KMRP's modules and Wine's Windows-side DLLs allocate from Wine's heaps; glibc's arena belongs to the native side (Mesa, Wine's Unix libraries). The corrupting write is therefore most likely native, with the textures at most its trigger.
- **The workbench reproduces it.** On 2026-10-16, opening the workbench on Dantooine to build the first lightsaber ended the game twice in two tries, after 90 and 23 minutes of play, with glibc's `munmap_chunk(): invalid pointer` and `free(): invalid pointer` on the main thread, with the original textures (this repair is not in the recipe). The session-history explanation above does not fit a crash that follows the screen.

The next evidence is a native stack at the abort with every thread: gdb attached to the running game, stopping only on `SIGABRT` (Wine uses the other signals itself), with a catchpoint whose commands do the capture, because an error inside a gdb command list abandons the rest of it. The script that does this is `data/logs/device/catch-abort.gdb`; attach it non-batch, its input held open, with `set sysroot /proc/<pid>/root` so the container's libraries resolve. Then the same route with this repair applied, which turns "candidate" into a yes or a no.

```bash
data/venv/bin/python repairs/07-kmrp-pot-gui-textures/make.py <dir with the three originals> /path/to/swkotor/Override
```

The originals are KMRP's own: the module extracts them into its run-time bank (`AppData\\Local\\Temp\\KMR*.tmp` in the prefix while the game runs), and the same three files are `assets/override-3440x1440/` in KMRP's repository. SHA-256 of 1.5.1's: `6159a972…052d`, `fca6aca1…d882`, `a0bee0df…7798`. None is kept here.
